# ClickHouse Observability POC

## Cerberus-based Loki Query Compatibility with ClickHouse

**Scope:** Logs only\
**Query gateway:** Cerberus\
**Reverse proxy:** NGINX\
**Storage/query engine:** ClickHouse\
**Visualization:** Existing Grafana\
**Query language:** LogQL-compatible Loki API

------------------------------------------------------------------------

## 1. Overview

This POC evaluates ClickHouse as a log storage and query backend while
retaining the existing Grafana Loki datasource interface for supported
query patterns.

The objective is to avoid immediately rebuilding existing Grafana
dashboards or rewriting every Loki query as ClickHouse SQL.

Query flow:

1.  Grafana sends a Loki-compatible HTTP request through its existing
    Loki datasource.
2.  NGINX receives the request.
3.  NGINX routes selected Loki read/query APIs to Cerberus.
4.  Cerberus parses supported LogQL expressions and generates ClickHouse
    SQL.
5.  ClickHouse executes the SQL against the configured logs table.
6.  Cerberus formats the result as a Loki-compatible response for
    Grafana.

**Current scope is logs only.** Tempo/traces and VictoriaMetrics/metrics
are not part of the current Cerberus validation.

## 2. Problem Statement and Objectives

The existing observability environment uses separate systems:

  Component         Responsibility                         Query interface
  ----------------- -------------------------------------- --------------------------
  Grafana Loki      Logs                                   LogQL / Loki HTTP API
  Grafana Tempo     Traces                                 TraceQL / Tempo HTTP API
  VictoriaMetrics   Metrics                                PromQL-compatible API
  ClickHouse        Analytical storage and SQL execution   SQL
  Grafana           Visualization and dashboards           Datasource APIs

Moving existing Loki dashboards directly to a ClickHouse datasource can
require panel query rewrites, LogQL-to-SQL conversion, and validation of
dashboard variables and query behaviour.

This POC tests whether a compatibility gateway can preserve the existing
Loki datasource interface for supported queries while ClickHouse handles
the underlying query execution.

### Goals

-   Retain the existing Grafana Loki datasource configuration.
-   Route supported Loki read APIs to Cerberus.
-   Translate supported LogQL expressions into ClickHouse SQL.
-   Query existing OpenTelemetry log data in ClickHouse.
-   Verify query execution using ClickHouse `system.query_log`.
-   Keep ingestion and query responsibilities separate.

### Not yet validated

-   Complete LogQL compatibility certification.
-   Migration of Tempo traces or VictoriaMetrics metrics.
-   Production-readiness certification.
-   Controlled performance comparison between Cerberus and Gigapipe.
-   Full one-to-one request-ID correlation from Grafana through NGINX
    and Cerberus to ClickHouse.

## 3. Cerberus: What Is It?

Cerberus is used as a query gateway between Grafana's Loki-compatible
API and ClickHouse.

At a high level, it accepts supported Loki-compatible requests, parses
the query expression, creates an internal query representation,
generates ClickHouse SQL, executes the query, and returns a
Loki-compatible response.

### Conceptual query flow

``` text
Grafana / Loki datasource
          |
          v
         NGINX
          |
          v
       Cerberus
          |
          | LogQL parsing and SQL generation
          v
      ClickHouse
          |
          v
    Query results
          |
          v
       Cerberus
          |
          v
        Grafana
```

### Example

Grafana query:

``` logql
{k8s_namespace_name="clickhouse"} |= "Warning"
```

Conceptual SQL equivalent:

``` sql
SELECT
    Timestamp,
    Body
FROM observability.otel_logs
WHERE
    ResourceAttributes['k8s.namespace.name'] = 'clickhouse'
    AND position(Body, 'Warning') > 0
ORDER BY Timestamp DESC;
```

This SQL is illustrative. The actual SQL generated by Cerberus can be
more complex and depends on the schema, query plan, and implementation.

### How Cerberus processes a query

1.  **API handler:** receives the Loki-compatible HTTP request, for
    example `/loki/api/v1/query_range`.
2.  **Parser:** parses the supported LogQL expression and identifies
    selectors and filters.
3.  **Internal query representation:** represents the parsed query in a
    structured form.
4.  **Planning/optimization:** prepares the query for execution.
5.  **SQL generation:** generates ClickHouse-compatible SQL.
6.  **ClickHouse execution:** executes SQL against the configured table.
7.  **Response formatting:** returns results in a Loki-compatible
    response format.

Cerberus is not the ingestion agent in this POC. Fluent Bit and OTel
agents write logs to their configured backends/tables. Cerberus handles
the read/query path.

## 4. Alternatives Considered

The following are relevant architectural alternatives. This is a
qualitative architecture comparison, not a formal benchmark.

### 4.1 Gigapipe (formerly Qryn)

Gigapipe, previously known as Qryn, is a broader ClickHouse-powered
observability platform with ingestion and compatible query interfaces.

Potential capabilities include: - Loki-compatible APIs and LogQL
support. - ClickHouse-backed log storage and querying. - Broader
observability interfaces for other telemetry types. - Ingestion
integrations.

**Why Cerberus was used for this POC:**

-   The immediate requirement was a separate query translation gateway.
-   Existing ingestion pipelines were to remain separate and unchanged.
-   The POC focused on querying an existing ClickHouse OpenTelemetry
    logs table.
-   Cerberus's query-gateway model aligned with this narrower scope.

This is an architectural fit decision, not proof that Cerberus is
universally better than Gigapipe. A controlled comparison using the same
dataset, query set, concurrency, and resource limits is needed to
compare performance and operational cost.

### 4.2 Grafana ClickHouse datasource plugin

This approach lets Grafana execute ClickHouse SQL directly.

**Advantages** - Direct SQL access to ClickHouse. - No separate LogQL
translation gateway is required.

**Trade-off for this POC** - Existing Loki panels use LogQL and Loki
APIs. - The ClickHouse datasource is not a drop-in translator for
existing LogQL dashboards. - Panels and queries may need to be rewritten
and validated.

### 4.3 cLoki

cLoki is another ClickHouse-backed Loki-compatible project and a
relevant alternative for evaluation.

It was not part of the completed hands-on comparison for this POC. Its
capabilities and compatibility should be validated against the actual
dashboard query set before making a selection decision.

### 4.4 Custom LogQL-to-SQL proxy

A custom proxy could parse LogQL and generate ClickHouse SQL.

**Advantages** - Full control over schema mapping and
application-specific behaviour.

**Trade-offs** - Parser and SQL generator development. - Maintaining
LogQL semantics. - Handling regex, pipeline stages, aggregations,
labels, and edge cases. - Long-term compatibility and testing
responsibility.

A pre-existing query gateway allowed this POC to focus on architecture
and backend validation rather than building a parser from scratch.

### 4.5 Continue using Loki

Continuing with Loki is the existing baseline and avoids migration work.
However, it does not evaluate ClickHouse as the log query backend and
retains a separate log storage system.

### Selection rationale

Cerberus was selected for this POC because its query-gateway
architecture matched the immediate requirement: preserve the existing
Loki-compatible Grafana interface while testing ClickHouse as the query
backend against the configured OpenTelemetry log schema.

No formal performance winner between Cerberus and Gigapipe has been
established.

## 7. NGINX Routing

The NGINX configuration defines separate Loki and Cerberus upstreams.

### Upstreams

``` nginx
upstream loki_backend {
  server loki-external.traditional-observability.svc.cluster.local:3100;
}

upstream cerberus_backend {
  server cerberus.cerberus.svc.cluster.local:8080;
}
```

### Push endpoint goes to Loki

``` nginx
location = /loki/api/v1/push {
  proxy_pass http://loki_backend;
}
```

### Supported read/query endpoints go to Cerberus

``` nginx
location ~ ^/loki/api/v1/(query|query_range|labels|label/|series|index/stats|index/volume|index/volume_range|detected_fields|detected_labels)(/|$) {
  proxy_pass http://cerberus_backend;
}
```

### Other paths fall back to Loki

``` nginx
location / {
  proxy_pass http://loki_backend;
}
```

### Routing summary

  Request path                 Configured upstream
  ---------------------------- ---------------------
  `/loki/api/v1/push`          Loki
  `/loki/api/v1/query`         Cerberus
  `/loki/api/v1/query_range`   Cerberus
  `/loki/api/v1/labels`        Cerberus
  `/loki/api/v1/label/...`     Cerberus
  `/loki/api/v1/series`        Cerberus
  `/loki/api/v1/index/stats`   Cerberus
  Unmatched paths              Loki fallback

The NGINX access log format currently records the request, status,
response bytes, referrer, user agent, and forwarded-for value. It does
**not** record the selected upstream address. Therefore, an HTTP 200
access-log entry alone does not prove which upstream handled the
request. Use routing configuration together with ClickHouse query-log
evidence.

## 8. Demo and Validation Runbook

Run the checks in this order during a demo.

### 8.1 Check Kubernetes pods

``` bash
kubectl get pods -n cerberus -o wide
kubectl get pods -n log-router -o wide
kubectl get pods -n clickhouse -o wide
```

Expected: relevant pods should be Running and Ready.

### 8.2 Check Cerberus readiness

If a port-forward is not already running:

``` bash
kubectl port-forward -n cerberus svc/cerberus 8081:8080
```

In another terminal:

``` bash
curl -i http://127.0.0.1:8081/readyz
```

Expected important fields:

``` json
{
  "clickhouse": "ok",
  "schema": "ready"
}
```

The current logs-only POC focuses on ClickHouse connectivity and schema
readiness. Other optional heads may show as closed and should be
interpreted according to the enabled scope.

### 8.3 Inspect effective NGINX configuration

``` bash
kubectl exec -n log-router deploy/log-router-nginx -- nginx -T
```

Check: - `loki_backend` - `cerberus_backend` - `/loki/api/v1/push` - The
regex location for read/query APIs - The fallback location

### 8.4 Inspect NGINX access logs

``` bash
kubectl logs -n log-router deploy/log-router-nginx --tail=100 --timestamps
```

For live observation:

``` bash
kubectl logs -n log-router deploy/log-router-nginx -f --since=1m
```

Example request:

``` text
GET /loki/api/v1/query_range?... HTTP/1.1" 200
```

Interpretation: - The request reached NGINX. - The requested API path
and HTTP status are visible. - The status does not independently prove
the selected upstream because the current log format does not include
`$upstream_addr`.

Common status codes: - `200`: successful HTTP response. - `499`: client
closed/cancelled the request. - `502`: bad gateway. - `503`:
service/upstream unavailable. - `504`: upstream timeout.

### 8.5 Verify Grafana datasource

In Grafana, open **Connections → Data Sources → `loki-1`**.

Current POC values:

``` text
Type: Loki
URL: http://127.0.0.1:32446
```

The datasource is retained as Loki-compatible. NGINX and Cerberus sit
behind the endpoint.

### 8.6 Run LogQL tests in Grafana Explore

Select datasource `loki-1`. Choose a time range containing available
logs, for example Last 15 minutes.

**Test 1 -- Exact label matcher**

``` logql
{k8s_namespace_name="clickhouse"}
```

Purpose: retrieve ClickHouse namespace logs.

**Test 2 -- Negative label matcher**

``` logql
{k8s_namespace_name!="clickhouse"}
```

Purpose: exclude ClickHouse namespace.

**Test 3 -- Regex label matcher**

``` logql
{k8s_namespace_name=~"clickhouse|logging"}
```

Purpose: match either namespace.

**Test 4 -- Negative regex label matcher**

``` logql
{k8s_namespace_name!~"clickhouse|logging"}
```

Purpose: exclude both namespaces.

**Test 5 -- Line contains**

``` logql
{k8s_namespace_name="clickhouse"} |= "Warning"
```

Purpose: return matching lines containing `Warning`.

**Test 6 -- Negative line filter**

``` logql
{k8s_namespace_name="clickhouse"} != "Warning"
```

Purpose: exclude lines containing `Warning`.

**Test 7 -- Regex line filter**

``` logql
{k8s_namespace_name="clickhouse"} |~ "Warning|Error"
```

Purpose: match lines containing either pattern.

**Test 8 -- Negative regex line filter**

``` logql
{k8s_namespace_name="clickhouse"} !~ "Warning|Error"
```

Purpose: exclude lines matching either pattern.

These are selected basic operator tests. They do not certify complete
LogQL compatibility.

### 8.7 Inspect ClickHouse database and table

Run in the ClickHouse client:

``` sql
SHOW DATABASES;
```

``` sql
SHOW TABLES FROM observability;
```

``` sql
DESCRIBE TABLE observability.otel_logs;
```

Inspect recent logs:

``` sql
SELECT
    Timestamp,
    ServiceName,
    Body
FROM observability.otel_logs
WHERE Timestamp >= now() - INTERVAL 15 MINUTE
ORDER BY Timestamp DESC
LIMIT 20;
```

Inspect namespace distribution:

``` sql
SELECT
    ResourceAttributes['k8s.namespace.name'] AS namespace,
    count() AS total_logs
FROM observability.otel_logs
WHERE Timestamp >= now() - INTERVAL 15 MINUTE
GROUP BY namespace
ORDER BY total_logs DESC;
```

### 8.8 Verify generated SELECT queries in ClickHouse

This is a key backend verification step.

``` sql
SELECT
    event_time,
    type,
    query_duration_ms,
    read_rows,
    substring(query, 1, 1500) AS generated_sql
FROM system.query_log
WHERE event_time >= now() - INTERVAL 10 MINUTE
  AND type = 'QueryFinish'
  AND query_kind = 'Select'
  AND query ILIKE '%otel_logs%'
ORDER BY event_time DESC
LIMIT 10;
```

Explanation: - `system.query_log`: ClickHouse query execution history. -
`event_time`: query-log event time. - `type = 'QueryFinish'`: completed
query events. - `query_kind = 'Select'`: read queries. -
`query ILIKE '%otel_logs%'`: query text references the logs table. -
`query_duration_ms`: ClickHouse execution duration. - `read_rows`: rows
read by the query.

A Cerberus-generated query may include expressions such as:

``` sql
SELECT
    `Body` AS `Line`,
    mapConcat(`ResourceAttributes`, ...)
```

The actual generated query can be substantially longer.

### 8.9 Verify a unique log-line filter

First run in Grafana Explore:

``` logql
{k8s_namespace_name="clickhouse"} |= "MergeMutateSelectedEntry"
```

Then run in ClickHouse:

``` sql
SELECT
    event_time,
    query_duration_ms,
    read_rows,
    query
FROM system.query_log
WHERE event_time >= now() - INTERVAL 10 MINUTE
  AND type = 'QueryFinish'
  AND query_kind = 'Select'
  AND query ILIKE '%otel_logs%'
  AND query ILIKE '%MergeMutateSelectedEntry%'
ORDER BY event_time DESC
LIMIT 5;
```

A matching generated SQL expression may look like:

``` sql
position(Body, 'MergeMutateSelectedEntry') > 0
```

This provides stronger evidence that the unique filter was translated
into SQL.

If no row is returned: - Re-run the Grafana query. - Confirm that the
selected time range contains the matching log. - Run the ClickHouse
query immediately afterwards. - Widen the query-log time window if
necessary.

A matching SQL expression and timestamp provide strong correlation.
Without a unique request ID propagated through the components, do not
claim strict one-to-one request correlation.

### 8.10 Inspect Cerberus logs

``` bash
kubectl logs -n cerberus deploy/cerberus --since=10m --tail=200
```

Live:

``` bash
kubectl logs -n cerberus deploy/cerberus -f --since=1m
```

The current `info` log level does not necessarily emit an access-log
line for every request. Empty Cerberus logs do not, by themselves, prove
that a query was not processed. Use readiness, NGINX routing
configuration, and ClickHouse query logs together.

## 9. Performance and Scalability

A query gateway adds processing stages: request handling, query parsing,
SQL generation, ClickHouse execution, and response formatting.

Total latency can depend on: - Gateway processing. - ClickHouse query
execution. - Data volume and time range. - Regex and filter
complexity. - Network transfer. - Response serialization. - Concurrent
query load.

Useful measurements:

  Metric                What it indicates
  --------------------- ------------------------------
  End-to-end latency    User-observed query time
  `query_duration_ms`   ClickHouse query duration
  `read_rows`           Rows read
  `read_bytes`          Bytes read
  CPU                   Processing consumption
  Memory                Query and gateway memory use
  Concurrent requests   Parallel workload handling
  Error rate            Failed requests

An observed query-log example in this POC recorded 151 ms ClickHouse
duration and 40,358 rows read. This is an observation from a test, not a
production benchmark.

Potential optimization areas include appropriate table ordering and
partitioning, materialized columns, suitable indexes/projections, query
limits, timeouts, resource isolation, and horizontal scaling of
stateless query gateways. Each optimization should be validated against
the real workload.

## 10. Known Limitations and Open Items

-   Complete LogQL compatibility has not been certified.
-   Basic label matchers and line filters have been tested.
-   Advanced parsing, aggregation, and edge-case expressions need
    additional validation.
-   Severity normalization (including `detected_level`) needs further
    investigation.
-   Current Cerberus `info` logs do not necessarily show every query
    request.
-   Current NGINX access log format does not include the selected
    upstream address.
-   Strict Grafana request-ID to ClickHouse query-ID correlation has not
    been established.
-   Cerberus restart history has not been fully root-caused.
-   Production-scale performance, concurrency, and cost benchmarks are
    pending.
-   Authentication, authorization, TLS, HA, backup/recovery, and
    production hardening require separate assessment.
